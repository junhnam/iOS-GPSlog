## ユーザーストーリー

ユーザー（jun さん）として、**履歴タブから過去の trip を開いたとき**、その日記録された滞留ピンをタップすれば店舗情報が詳細シートで見られ、Apple Maps / Google Maps で再訪したい場所をすぐ開けるようにしたい。なぜなら、S6-011 で「地図タブ」のピンタップ詳細は実装したが、jun さんの実機検証 2 回目で **触っていたのは履歴タブの方**であり、履歴タブで同じ操作をしても標準 InfoWindow（吹き出し）しか出ないため「結局過去のお店情報が活用できない」状態になっているから。あわせて、お店情報欄に住所が紛れて表示される（POI ヒット 0 件のとき `placeName` に住所が入る）バグも同時に潰し、UX の最終仕上げとする。

## 技術メモ

### Swift 6 strict concurrency と GMSMapViewDelegate

S6-011 で `MapView.Coordinator` を `GMSMapViewDelegate` 準拠させた際、`@preconcurrency` を付けないとビルドエラーになる事象が確認されている。同じ問題が履歴側でも起こるため、**最初から `@preconcurrency final class Coordinator: NSObject, GMSMapViewDelegate` で書くこと**。これが本チケットの一番のハマりどころ。

### Coordinator から SwiftUI への通知方法

GMSMapViewDelegate メソッドは `@MainActor` の保証がない（`@preconcurrency` で吸収）。SwiftUI の `@State` を更新する経路は 2 案:

1. **Closure 注入**: `HistoryDetailMapContainer` の init で `onPinTap: (PinRecord) -> Void` を受け取り、`makeCoordinator` で Coordinator に渡す。Coordinator は closure を呼ぶだけ。SwiftUI 側は closure 内で `selectedPin = ...` をセット
2. **Binding 注入**: `@Binding var selectedPin: RestoredPin?` を `HistoryDetailMapContainer` に渡す → Coordinator にバインディングを保持させる（Sendable 境界に注意）

**1 を推奨**。closure の方が Sendable 関連のコンパイラ警告を回避しやすく、テストもしやすい（Coordinator にハンドラ closure を直接差し替えて検証可能）。

### B 修正の差分（メイン代行が既に当てた変更 / 参考）

// LocationService.swift:739 周辺（修正後）

### 個人利用版 jun さんへの「履歴画面の挙動修正＝最後の体験バグ」の重要性

**最重要**。理由:

1. 個人利用版で jun さんが日々使う中心動線は「今日の地図」（地図タブ）と「過去の記録の振り返り」（履歴タブ）の **両方**
2. 地図タブだけ詳細シートが出て、履歴タブは出ない、という状態は「機能の不整合」として強い違和感を残す（同じピンの UI が文脈で挙動が変わる）
3. CLAUDE.md 要件「ピンにはその場所のお店情報などを紐付ける」は、過去履歴の振り返りでこそ価値が出る（「先週行ったあのお店どこだっけ → 履歴で見る → ワンタップで Maps」というユースケースが本命）
4. このバグを残したまま「Sprint 6 完了 / リリース」とすると、個人利用版とはいえ完成度の判定基準を満たさない

### リスクの所在

- **GMSMapViewDelegate 準拠で Swift 6 strict concurrency に引っかかる可能性**: S6-011 で同じ罠を踏み `@preconcurrency` で解決済 → 既知パターンを再利用するだけなのでリスク低
- **`marker.userData` の Sendable 警告**: `PinRecord` が `@Model` クラスなので Sendable ではない。S6-011 では `RestoredPin` を marker.userData に詰めることでこの問題を回避済 → **本チケットでも RestoredPin を詰める方針を踏襲**（PinRecord を直接詰めない方が安全）
- **B 修正取り込み忘れ**: メイン代行の手元修正が未コミット状態。dev エージェントが S6-013 着手時に `git diff` を確認してから作業しないと、A だけコミットして B が抜ける事故になる → **コミット前に `git status` / `git diff` で B 修正がステージに含まれているか必ず確認するよう dev 指示書に明記**

### Sprint 6 内で間に合わない場合の代替

- 半日想定なので、ほぼ間に合わないリスクはない
- 万一間に合わない場合: B 修正のみ先行コミット（リグレッション無し / placeName に住所が混じらなくなるだけ）→ A は Sprint 7 切り出し
