## ユーザーストーリー
PO/SM として、Sprint 4 / 5 で連続発生した「依存組立漏れ」型の Critical/High バグが Sprint 6 で再発しないように、新規サービス追加時に必ず DI 経路の統合テストを書く運用を定型化したい。なぜなら、仕組みで防がないと同じバグが Sprint 6 でも繰り返される蓋然性が高いから。

## 技術メモ

### 背景

- Sprint 4 で QA-S4-001 (CalendarSyncService の依存漏れ) 発生
- Sprint 5 で QA-S5-001/002 (CloudUploadCoordinator / CloudUploadRetryQueue の依存漏れ + .task 起動漏れ) 発生
- いずれも RootView.init で部品を組み立てる際の漏れが原因
- ユニットテスト単体では検出できず、統合テストで初めて発見されている

### 雛形コメントの記入例（参考）

```swift
// MARK: - DI 経路カバレッジ
// 新規サービス / 新規 @Model を追加した場合は、ここに以下のケースを追加すること:
// 1. RootView の init で当該サービスがインスタンス化されているか
// 2. 依存先（LocationService 等）に正しく注入されているか
// 3. .task または onAppear で起動時処理が発火するか
// 4. AppSettings に新規プロパティが追加されている場合、デフォルト値が想定通りか
//
// 参考: Sprint 5 QA-S5-001/002 (CloudUploadCoordinator / RetryQueue の DI 漏れ)
```
