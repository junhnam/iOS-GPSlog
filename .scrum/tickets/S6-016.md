## ユーザーストーリー

ユーザー（jun さん）として、**常時同期モードでアプリを起動し、地図タブ以外のタブ（設定 / 履歴）を見たり、その状態でアプリをタスクキルしたりしても、移動が始まれば自動的に記録が継続・再開されてほしい**。なぜなら、CLAUDE.md 記載のコア要件「常時同期 ON の場合は自動的に記録」は、ユーザーが画面を切り替えるかどうかと無関係に成立すべき仕様であり、無意識に「タブを切り替えると記録が止まる」挙動が混入すると、ユーザーの想定と実挙動が乖離し、何 km 走っても何も記録されない致命的体験を生むから。

---

## 背景（実機検証 5 回目フィードバック / 2026-05-12）

S6-015 完了後、jun さんが iPhone 16 Pro 実機で 2026-05-12 に行った実利用検証で発覚した致命バグ。

### 観測された事象

- 常時同期 ON の状態で **10km 運転**
- アプリは運転中タスクキルされたまま（一度も起動していない）
- 帰宅後にアプリを開くと **移動経路もピンも一切記録されていなかった**

### Console.app 実機ログによる切り分け

- iOS 側は GPSLogger に位置情報を正常に送信していた
- → iOS の送出は問題なく、**アプリ内で「タスクキル後の SLC で起動しない / GPS を再開しない」経路にバグが残っていた**
- S6-015 の保険ロジック（`wasTracking=true` ガード + `didUpdateLocations` 冒頭の `needsResume` 経路）はいずれも `wasTracking=true` を前提に成立する設計だったが、**実機では `wasTracking` が `false` に落ちていた** ことを示す

### 期待される挙動

- 常時同期 ON にしている限り、タブ切替・タスクキルに関わらず移動が始まれば記録が（再）開始される

### 実際の挙動

- 地図タブを離れた瞬間に GPS が停止し、`wasTracking=false` で永続化される
- 翌日タスクキル状態で SLC 起床しても、S6-015 の `wasTracking=true` ガードが false で発火せず記録再開しない

---

## 根本原因（メイン代行が特定済）

**[`GPSLogger/Features/Map/MapView.swift:108-110`](../../GPSLogger/Features/Map/MapView.swift) の `.onDisappear` で `stopUpdatingLocation()` を呼んでいる**:

```swift
.onDisappear {
    locationService.stopUpdatingLocation()  // ← これがバグの源
}
```

そして `LocationService.stopUpdatingLocation()` の中で **`wasTracking = false` にリセットされる**（`LocationService.swift:228`）。

```swift
func stopUpdatingLocation() {
    ...
    manager.stopUpdatingLocation()
    // S6-006: 意図的な記録停止なので wasTracking を false にリセットする。
    appSettings?.wasTracking = false
}
```

### 発生メカニズム（ステップ）

1. アプリ起動 → 地図タブ表示 → `.onAppear` で常時同期なら `startUpdatingLocation()` → **`wasTracking = true`**
2. jun さんが設定タブ or 履歴タブに切り替え → 地図タブの **`.onDisappear` 発火** → `stopUpdatingLocation()` → **`wasTracking = false`**
3. その状態でタスクキル → **`wasTracking = false` のまま永続化（UserDefaults）**
4. 翌日アプリ未起動のまま運転 → SLC でアプリが起床 → S6-015 で実装した **「`wasTracking=true` なら復帰」ガードが false で発火せず、記録再開しない**
5. `didUpdateLocations` 冒頭の `needsResume = !isUpdating && wasTracking` 保険経路も `wasTracking=false` のため発火しない
6. **結果: 10km 運転しても何も記録されない**

### S6-015 が見落とした理由

S6-015 のテストは「意図的に `wasTracking=true` を立てた状態」を前提にしていた。実機では `wasTracking` がタブ切替で false になっていることを見逃した（テストは S6-015 で導入した経路の妥当性は検証していたが、その入力前提が現実と乖離していた）。

つまり S6-015 の wasTracking ガード自体は正しい設計だが、その値を破壊する経路（`.onDisappear` → `stopUpdatingLocation`）を残していたため、ガードの効力が事実上ゼロになっていた。

---

## 修正方針（dev-2 が並行実装中）

`MapView.swift` の `.onDisappear` の `stopUpdatingLocation()` を **削除** する。

### 削除する理由

1. **CLAUDE.md 仕様違反**: 「常時同期は自動的に記録」は本来タブ切替と独立した挙動であるべき
2. **UX として誤り**: ユーザーは地図タブを離れる = 記録停止 を意図していない（明示停止は別 UI で行うべき）
3. **トリガーモードは別経路で停止可能**: 既存の `RecordingToggleButton`（floating button）で明示的に開始 / 停止できるため、`.onDisappear` で副次的に停止する必要はない
4. **バッテリー懸念は S6-005 が吸収**: 「タブ切替で止まらない = 常に GPS」になることのバッテリー影響は、S6-005 で実装した `BatteryAdaptiveLocationPolicy`（停車中は低精度 + distanceFilter 動的）でカバー済

**個人利用版リリース判定の前提条件 / リリースブロッカー**。

本バグは、現状の修正済みコード（S6-015 まで）でも **jun さんの実機検証で「タブ切替後の記録継続」が壊れていることを示す致命例**。S6-015 の `wasTracking` ガードは設計として正しいが、その値を破壊する経路（`.onDisappear` 副作用）を残していたため、SLC 起床経路の保険ロジック群が全て無効化されていた。

このバグが残ると:

- 「常時同期 ON にしているのに、知らないうちに記録が止まっている」最悪の体験が再発する

- jun さんの 5/12 検証で「10km の移動が完全に拾われない」事例として既に発生済 → アプリへの信頼が崩れる致命的体験

→ **Must / リリースブロッカー** で確定。Sprint 6 完了基準に組み込む。

## レビュー観点（コードレビューエージェント向け）

dev-2 のコード PR をレビューする際、以下を必ず確認すること:

1. **`.onDisappear` を削除することの副作用**
   - 他のライフサイクル経路で `stopUpdatingLocation` が暗黙に必要だった依存はないか（メモリ解放 / マネージャの後始末 / Combine の購読解除など）
   - `MapView` が破棄される（戻る操作 / タブグループの構造変更）ケースで GPS マネージャがリークしないか

2. **バッテリー消費への影響**
   - 「タブ切替で止まらない = 常に GPS」となることの影響を S6-005（`BatteryAdaptiveLocationPolicy`）がきちんと吸収しているか
   - 停車中は低精度 + 大きい distanceFilter / 走行中は高精度に切り替わる経路が、地図タブ非表示状態でも動作するか
   - `pausesLocationUpdatesAutomatically = true`（S6-005 で確認済）が現状有効であり、本修正後も尊重されるか

3. **`wasTracking` フラグの他の使用箇所への波及**
   - `resumeTrackingAfterRelaunch`（`LocationService.swift:336-368`）: `wasTracking=true` ガードで再開判定 → 本修正で `wasTracking=true` が維持されるため、想定通りに発火する
   - `startTrackingFromSLC`（S6-006）: 同上、`wasTracking` が破壊されない前提で動作する
   - `handleHomeStateTransition`（`LocationService.swift:520-534`）: `current != .atHome` && `wasTracking=true` ガード（S6-015）が機能する
   - `didUpdateLocations` 冒頭の `needsResume = !isUpdating && wasTracking`（S6-015）: 同上
   - これらの経路が「`wasTracking=true` を維持できなかった場合のフォールバック」を期待していないか（していないことを確認）

4. **既存テストへの影響**
   - `LocationServiceTests` 系: `stopUpdatingLocation` 呼び出し前提のテストが MapView 経由のものを含んでいないか
   - `MapViewTests` 系（存在する場合）: `.onDisappear` 期待のアサーションがないか
   - S6-006 で導入した `wasTracking` 永続化テスト群が新仕様（タブ切替で false にならない）に整合しているか

5. **トリガーモード時の挙動が壊れていないこと**
   - `handleRecordingToggle` 経由の `stopUpdatingLocation` 呼び出しは残っていること
   - `RecordingToggleButton` でユーザーが明示停止した場合、`wasTracking=false` で永続化される挙動が維持されていること
   - トリガーモードでアプリ起動時に自動 start しない既存仕様（S3-004 / S3-005）が維持されていること
