## ユーザーストーリー
ユーザーとして、移動中に電波が弱い場所でクラウド同期が失敗した時、後で電波が回復した時に自動的に再アップロードされてほしい。なぜなら、「同期されたつもりが実は失敗していた」という事故を防ぎたいから。

## 受け入れ条件

- [ ] `Services/Cloud/CloudUploadRetryQueue.swift` を新規作成
- [ ] アップロード失敗時、`(tripRecord.id, retryCount, lastError)` をローカル永続化（UserDefaults または SwiftData の専用テーブル）
- [ ] アプリ起動時 + ネットワーク回復時（`NWPathMonitor`）にキューを処理し、未送信分を再アップロード
- [ ] リトライ回数の上限: 5 回（指数バックオフ: 30秒 → 1分 → 2分 → 5分 → 10分）
- [ ] 5 回失敗した場合は `UNNotification` でローカル通知（「クラウド同期に失敗しました。設定から手動同期してください」）
- [ ] 設定画面の「データ」セクションに「未同期 N 件」のバッジを表示
- [ ] 設定画面から「未同期分を手動同期」ボタンを押すとキューを即時実行
- [ ] ユニットテスト: 失敗 → 永続化 → 成功 → キューから削除 / 5 回失敗 → 通知発火 / ネットワーク回復時の自動実行 / バッジ表示の 4 ケース以上

## 技術メモ

### 永続化の選択

- 案 A（推奨）: SwiftData の `@Model PendingUpload`（`tripID: PersistentIdentifier`, `retryCount: Int`, `lastErrorMessage: String?`, `lastTriedAt: Date`）を新規作成
- 案 B: UserDefaults に Codable な配列を保存（軽量だが SwiftData との重複管理になる）

→ 案 A を採用。理由: 移動記録自体が SwiftData 管理なので、同期キューも同じ SwiftData コンテナで管理した方が一貫性がある。

### 通知権限

- `UNUserNotificationCenter.requestAuthorization(options: [.alert, .badge, .sound])` を初回失敗時に要求
- 拒否された場合は通知をスキップし、設定画面のバッジ表示のみで対応

### iOS 26 / Swift 6 strict concurrency

- `NWPathMonitor` は MainActor 外で動くので、Task で MainActor へブリッジ

### iOS 26 SwiftData 注意点

- `.scrum/notes/ios26-swiftdata.md` の「@Relationship 配列に default 値を設定」「ModelContainer を強参照保持」など既知の落とし穴を踏まないこと
- `PendingUpload` は単一エンティティ（リレーション無し）の想定なので比較的安全
