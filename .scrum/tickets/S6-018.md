## ユーザーストーリー

ユーザー（jun さん）として、**タスクキル後・OS による kill 後・SLC バックグラウンド起床時のいずれにおいても、アプリ側の依存オブジェクト（LocationService / AppSettings / TripRepository / AppDelegate）が確実に生成されて GPS 受信を再開できる状態であってほしい**。なぜなら、依存オブジェクトの生成が SwiftUI の `WindowGroup.body` 評価まで遅延される現行構造では、バックグラウンド SLC 起床時に body が評価されないため `LocationService` が存在せず、iOS から配信される位置情報を受け取れる主体がいない（= 記録不可能）状態が継続してしまうから。

---

## 背景（2026-05-19 QA オーケストレーター全体検証）

S6-015 / S6-016 / S6-017 で「タスクキル後の自宅 → 再出発」「タブ切替後の記録停止」「SLC 空白ウィンドウ」を連続して修正し、ユニットテストもすべて pass している。しかし 2026-05-19 jun さん実機検証で **タスクキル中は GPS が一切反応しない** 症状が再発した。

メイン代行が S6-018（UIApplicationDelegateAdaptor 欠落）として準備していたが、QA オーケストレーターによる全体検証で **S6-018 単独では症状の 60-70% しか解消しない** ことが判明。残る 30-40% は S6-019（pausesLocationUpdatesAutomatically の方針 + delegate 実装欠落）と、構造的検出漏れに対する S6-020（ライフサイクル統合テスト）でようやくカバーされる。

本チケットは **DI 経路の確実化** に絞った修正。

## 根本原因

### 1. `@State` 遅延評価による DI 不成立

現行 `App.swift`:

```swift
@main
struct GPSLoggerApp: App {
    @State private var dependencies = AppDependencyContainer()  // ← この行が問題

    var body: some Scene {
        WindowGroup {
            RootView(dependencies: dependencies)
        }
    }
}
```

SwiftUI の `@State` は **WindowGroup の body が初めて評価された時点** で初期化される。タスクキル後に iOS が SLC でアプリを起床する場合:

| ケース | body 評価 | dependencies 生成 | LocationService 存在 |
|---|---|---|---|
| ユーザーがアプリアイコンをタップして起動 | される | される | する |
| SLC 起床 / バックグラウンド起動 / `UIBackgroundModes: location` 復帰 | **されない**（UI 描画が走らない） | **されない** | **しない** |

→ iOS は位置情報を配信しているが、受け取る主体（`LocationService` の `CLLocationManager` delegate）が存在しないため、何も記録されない。

### 2. AppDelegate 経路の欠落

iOS の位置情報サービスがバックグラウンドでアプリを起床させる際、最初に呼ばれるのは `UIApplicationDelegate.application(_:didFinishLaunchingWithOptions:)`。SwiftUI App ライフサイクルでは `UIApplicationDelegateAdaptor` を使わない限り AppDelegate が存在しないため、起床直後に依存性を組み立てる隙がない。

`launchOptions[.location] != nil` の判定もできない（= 「これは位置情報による起床である」を検知できない）。

---

## 修正方針

### A: `UIApplicationDelegateAdaptor` 導入

```swift
@main
struct GPSLoggerApp: App {
    @UIApplicationDelegateAdaptor(AppDelegate.self) private var appDelegate

    // @State から @ObservedObject に変更（AppDelegate が所有）
    @ObservedObject private var dependencies: AppDependencyContainer

    init() {
        // ここで生成しておく。@State の遅延評価に依存しない
        let container = AppDelegate.shared?.dependencies ?? AppDependencyContainer()
        _dependencies = ObservedObject(initialValue: container)
    }

    var body: some Scene {
        WindowGroup {
            RootView(dependencies: dependencies)
        }
    }
}
```

### B: `AppDelegate` の実装

```swift
final class AppDelegate: NSObject, UIApplicationDelegate {
    static private(set) var shared: AppDelegate?

    let dependencies = AppDependencyContainer()

    func application(
        _ application: UIApplication,
        didFinishLaunchingWithOptions launchOptions: [UIApplication.LaunchOptionsKey: Any]? = nil
    ) -> Bool {
        AppDelegate.shared = self

        // 位置情報による起床経路をログ
        if launchOptions?[.location] != nil {
            // SLC / region monitoring 起床
            dependencies.locationService.handleBackgroundLaunchFromLocation()
        }

        return true
    }
}
```

### C: `App.init()` でも生成（保険）

`AppDelegate.application(_:didFinishLaunchingWithOptions:)` は呼ばれるはずだが、SwiftUI Scene の構築順序によっては `App.init` が先に走るケースもある。両方で生成しても問題ないよう、`AppDependencyContainer` 側を冪等にする or shared を介して同一インスタンスを返す設計にする。

### D: `@StateObject → @ObservedObject` 変更

`AppDelegate` がライフサイクルの起点になったため、`App` 側で `@State` / `@StateObject` で所有する必要はない。`AppDelegate.dependencies` を `@ObservedObject` として `App` が観測する形に変更する。

## レビュー観点（dev-2 完了後 / general-purpose レビューエージェント向け）

1. **AppDelegate と App 構造体の二重生成回避**
   - `AppDelegate.dependencies` と `App.init` 内の生成が同一インスタンスを指すか（`shared` 経由）
   - 2 重生成された場合に CLLocationManager の delegate が後勝ちで上書きされないか
   - 推奨実装: `AppDependencyContainer` を **単一インスタンス確認** にし、2 回目以降の生成は warning ログ + 既存インスタンスを返す形（or fatalError）

2. **`@ObservedObject` 化による副作用**
   - SwiftUI の再描画頻度が増えないか（`@Published` の発火源を確認）
   - 既存 `RootView` の `@StateObject` ベースのテストが壊れないか

3. **`launchOptions[.location]` の検知タイミング**
   - AppDelegate.didFinishLaunchingWithOptions の中で `LocationService` の delegate 設定までが完了するか
   - 起床直後の `didUpdateLocations` を取りこぼさないか（delegate 設定が間に合うか）

4. **Info.plist の整合性**（**注意喚起**）
   - 過去に dev エージェント実行時に Xcode 関連処理（GenerateAssetSymbols 等）で Info.plist が巻き戻る事案があった（Sprint 6 中盤）
   - 本修正で `UIBackgroundModes: location` / `NSLocationAlwaysAndWhenInUseUsageDescription` 等が消えていないか **必ず確認**
   - `LSApplicationQueriesSchemes: comgooglemaps`（S6-011 で追加）の保全も確認
   - レビュー時は `git diff -- GPSLogger/Info.plist` を必ず参照する

5. **AppDelegate.shared の static var**
   - Swift 6 strict concurrency における `@MainActor` の扱い
   - テストでの差し替え可能性（init 時に注入する形にしない方が良い理由）

6. **既存 256 件テストへの回帰**
   - 「mock manager を直接渡す」スタイルのテストが、AppDelegate 経由になった後も成立するか
   - S6-020 の新規ライフサイクル統合テストとの責務分離（重複しないか）
