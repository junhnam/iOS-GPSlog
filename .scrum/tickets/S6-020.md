## ユーザーストーリー

開発チームとして、**SwiftUI App ライフサイクル（App.init → UIApplicationDelegateAdaptor.didFinish → WindowGroup.body 評価 → @State / @StateObject 初期化）の連鎖が「依存オブジェクトと delegate を確実に立てる」ことを、ユニットテストレベルで検証できる状態が欲しい**。なぜなら、既存 256 件のテストはすべて「mock manager を直接渡す」スタイルでサービス層を検証しており、SwiftUI ライフサイクル経由の DI 経路を 1 件も検証していないため、S6-015 / S6-017 のような「ユニットテストは pass するのに実機で機能しない」構造的バグを Sprint 7 以降で繰り返す可能性が高いから。

---

## 背景（2026-05-19 QA オーケストレーター全体検証）

### 既存 256 件テストの構造的限界

S6-001 で導入した DI カバレッジテストの定型化は、**「`AppDependencyContainer` を直接生成して中身を検証する」レベル** で運用されている。一方、実機での GPS 起床経路は:

```
iOS が SLC でアプリ起床
  → UIApplicationDelegateAdaptor.application(_:didFinishLaunchingWithOptions:)
    → AppDelegate.dependencies 生成（S6-018）
      → CLLocationManager.delegate = locationService（S6-018）
        → didUpdateLocations 配信
          → handleNewLocations / handleHomeStateTransition / resumeTrackingAfterRelaunch
```

の連鎖を辿る。既存テストはこの **連鎖の入り口（App.init / AppDelegate.didFinish / WindowGroup.body 評価）を一切検証していない**。

S6-015 / S6-016 / S6-017 で `LocationService` 内部のロジックを修正し、それぞれ 4 / 3 / 3 件のユニットテストを追加して pass したが、**実機検証で症状が再現** したのはこのライフサイクル連鎖が壊れていたため。

### QA オーケストレーターの指摘

> 既存 256 件は「mock manager を直接渡す」スタイルで、SwiftUI App → WindowGroup.body → @State 初期化 のライフサイクル連鎖を 1 件も検証していない。これが S6-015 / S6-017 の修正が pass するのに実機で機能しない構造的原因。

→ 本チケットで **ライフサイクル統合テスト** を追加し、構造的検出漏れを潰す。

## 修正方針

### A: 新規テストファイル `LocationServiceLifecycleIntegrationTests.swift`

`GPSLoggerTests/Integration/LocationServiceLifecycleIntegrationTests.swift` を新規作成し、以下を検証:

#### T-1: 通常起動経路（アプリアイコンタップ）

```swift
@MainActor
func test_normalLaunch_dependenciesAndDelegateAreSet() async throws {
    // 1. AppDelegate を生成（実際の AppDelegate を使う / shared に登録）
    let appDelegate = AppDelegate()
    _ = appDelegate.application(
        UIApplication.shared,
        didFinishLaunchingWithOptions: nil
    )

    // 2. dependencies が生成されていること
    XCTAssertNotNil(AppDelegate.shared)
    XCTAssertNotNil(AppDelegate.shared?.dependencies)

    // 3. CLLocationManager の delegate が LocationService に設定されていること
    let locationService = appDelegate.dependencies.locationService
    XCTAssertTrue(locationService.isManagerDelegateSet)
}
```

#### T-2: SLC 起床経路（launchOptions[.location] 経由）

```swift
@MainActor
func test_slcLaunch_dependenciesAndDelegateAreSet() async throws {
    let appDelegate = AppDelegate()
    let launchOptions: [UIApplication.LaunchOptionsKey: Any] = [
        .location: true
    ]
    _ = appDelegate.application(
        UIApplication.shared,
        didFinishLaunchingWithOptions: launchOptions
    )

    // dependencies が生成されていること
    XCTAssertNotNil(appDelegate.dependencies)

    // SLC 起床経路の処理が呼ばれていること
    XCTAssertTrue(appDelegate.dependencies.locationService.didHandleBackgroundLaunchFromLocation)
}
```

#### T-3: App.init 経路と AppDelegate 経路の同一インスタンス保証

```swift
@MainActor
func test_appInit_returnsSameInstanceAsAppDelegate() async throws {
    let appDelegate = AppDelegate()
    _ = appDelegate.application(
        UIApplication.shared,
        didFinishLaunchingWithOptions: nil
    )

    // App.init() 内で参照される dependencies が AppDelegate.shared.dependencies と同一であること
    let containerFromApp = AppDelegate.shared?.dependencies
    XCTAssertTrue(containerFromApp === appDelegate.dependencies)
}
```

#### T-4: WindowGroup.body 評価時に dependencies が確実に存在する（フォールバック検証）

```swift
@MainActor
func test_windowGroupBody_dependenciesAvailable_whenAppDelegateAlreadyRan() async throws {
    // AppDelegate が先に走ったケース
    let appDelegate = AppDelegate()
    _ = appDelegate.application(
        UIApplication.shared,
        didFinishLaunchingWithOptions: nil
    )

    // App.init を simulate（AppDependencyContainer の取得経路を検証）
    let containerFromBody = AppDelegate.shared?.dependencies ?? AppDependencyContainer()
    XCTAssertNotNil(containerFromBody)
    XCTAssertTrue(containerFromBody === appDelegate.dependencies)
}
```

#### T-5: AppDelegate 経路の冪等性（2 重生成保護）

```swift
@MainActor
func test_appDelegate_doesNotCreateDuplicateDependencies() async throws {
    let appDelegate = AppDelegate()
    _ = appDelegate.application(UIApplication.shared, didFinishLaunchingWithOptions: nil)
    let first = appDelegate.dependencies

    _ = appDelegate.application(UIApplication.shared, didFinishLaunchingWithOptions: nil)
    let second = appDelegate.dependencies

    XCTAssertTrue(first === second, "AppDelegate.dependencies は冪等であるべき")
}
```

### B: `LocationService` 側に検証用フラグ追加（test-only / debug 専用）

#if DEBUG
extension LocationService {

## レビュー観点（dev-2 完了後 / general-purpose レビューエージェント向け）

1. **`UIApplication.shared` の扱い**
   - テスト内で `UIApplication.shared` を呼ぶと XCTest の制約（unit test bundle で UIKit App 環境が完全に成立しない）に当たる可能性
   - 推奨: `UIApplication` をモック化 or `XCTSkip` 戦略 or `@testable import` で AppDelegate のみ検証する

2. **`AppDelegate.shared` の static var の取り扱い**
   - テスト間でリークしないか（`setUp` / `tearDown` でリセット）
   - Swift 6 strict concurrency の `@MainActor` との整合

3. **テストの責務分離**
   - S6-018 のユニットテスト（AppDependencyContainer 単体）と本テスト（ライフサイクル統合）の重複が無いか
   - 「単体テストでは検証できない経路」だけを本テストで担保する設計か

4. **XCUITest との関係**
   - 本チケットは XCTest level の統合テスト
   - 実機 / シミュレータレベルの真のライフサイクル検証は XCUITest が必要
   - Sprint 7 への XCUITest 整備提案として `.scrum/notes/qa-review-2026-05-19.md` に明示

5. **DEBUG ビルド限定フラグ**
   - `#if DEBUG` で追加するフラグが Release ビルドに混入しないこと
   - フラグの命名規則（`is...Set` / `didHandle...`）が既存コードと整合するか
