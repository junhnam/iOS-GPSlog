## ユーザーストーリー

ユーザー（jun さん）として、大型のショッピングモール / 家電量販店 / レストラン街など、店内回遊で 30m 以上歩く店舗に 20 分以上滞在しても、ちゃんとピン 1 件として記録されてほしい。なぜなら、現状の半径 30m 設定では「同一店舗内で歩いている」のを「店外に出た」と誤判定してアンカーが切り替わってしまい、累積滞留時間が `minDuration` に届かないまま 0 件になってしまうから。

---

## 背景（実機検証フィードバック / 2026-05-09）

jun さんが iPhone 16 Pro 実機検証（2026-05-09 夕方）で:

- **4 店舗で各 20 分滞在 → ピン 1 件しか立たなかった**

### 原因の推定（メイン代行 Explore 結果）

- `StayDetector.radiusMeters` のデフォルトが **30m**（[`StayDetector.swift:13`](../../GPSLogger/Services/Trip/StayDetector.swift)）
- 大型店舗内で店内回遊（30m 以上歩く）が起きると:
  1. アンカーから 30m 外に出た時点で `ingest` が「半径外」と判定
  2. 累積時間 < `minDuration`（600 秒）ならピン未生成のまま新アンカーへ
  3. 新アンカーでまた数分歩いて再離脱 → 同じ動作の繰り返し
  4. 結果として「20 分滞在したのにピン 0 件」になる

特に以下の店舗形態で顕著:
- ショッピングモール（イオン / ららぽーと等）: 100m 以上の店舗が多い
- 家電量販店（ヨドバシ / ビックカメラ）: フロア面積が広い
- レストラン街・フードコート: 席移動 + トイレ往復で数十 m 歩く
- 大型ホームセンター: 100m 超えの店も

  - 念のため `RetroactiveStayDetector` 側でも値を確認・コメント追記する
- [ ] **冪等性ガードの半径**（`RetroactiveStayDetector.isDuplicate` 内の `config.radiusMeters` 利用箇所 / [`RetroactiveStayDetector.swift:143`](../../GPSLogger/Services/Trip/RetroactiveStayDetector.swift)）:
  - 現状は `StayDetectionConfig.radiusMeters` を共有 → 100m に追従する
  - **判断**: 冪等性ガードも 100m に揃える（**コードはそのまま / 共有 config 経由で自動追従**）
  - 理由: 後追い検知の半径と冪等判定の半径を別値にすると「後追いで検知されるが冪等チェックで通らない」ケースが出てバグの温床になる
  - 副作用: 100m 圏内 + 5 分以内の既存ピンと「同一」とみなされる範囲が広がる → 隣接する別店舗のピンが「同一扱い」されて二重作成されないリスクは増えるが、**stayedFrom 5 分差** の時間ガードが効くため実用上は問題ない（同じ場所に同時刻 5 分差で 2 回滞留することは現実的にレア）
  - もし別値にしたい場合は `StayDetectionConfig` に `idempotencyRadiusMeters` を追加する設計が必要 → 今回は **やらない**（YAGNI）

## トレードオフのメモ（重要）

### 100m 採用のメリット

- 大型店舗（モール / 家電量販店 / レストラン街）で店内回遊しても累積滞留時間が分断されない
- jun さんの実機シナリオ（4 店舗 20 分 → ピン 1 件）を解消できる
- CLAUDE.md「お店情報を紐付ける」要件の実用性が向上（大型店こそ「どこ行ったか」を後で見たい）

### 100m 採用のデメリット / 副作用

- **隣接する別店舗を同一視するリスク**:
  - 例: コンビニ A の前にバス停（半径 50m）→ コンビニ A に入店 → 同じ「100m アンカー」と扱われ、コンビニ A の滞留判定が遅れる可能性
  - 例: 商店街で「店 A → 隣の店 B」と移動した場合、別ピンとして記録されず 1 件にマージされる
  - 個人利用としての許容判断: jun さんは「大型店優先」を明確に選択（2026-05-09）
- **GPS 精度誤差を吸収しすぎる**:
  - kCLLocationAccuracyBest = 約 5〜10m に対し、100m は 10〜20 倍の余裕
  - 屋内 / 高層ビル谷間で精度が落ちた場合に「移動したのに同じ場所」と判定するリスクは増える
- **MKLocalSearch の精度との不整合**:
  - PlaceLookupService が拾うお店情報は座標 ±数十 m の精度に依存
  - 100m 圏内に複数店舗がある繁華街では「ピンの座標」と「実際に滞留した店舗」がズレる可能性
  - → 個人利用版では許容（S6-011 で住所 + 外部マップ起動を提供しているのでズレは事後修正可能）

### Sprint 7 以降の見直し材料

- 設定画面で半径を可変にするオプション（jun さん「不要」判断 / 商用化時に再考）
- 滞留判定アルゴリズムの精緻化（密度ベース / クラスタリング / 移動速度連動）
- 「店舗内回遊」と「店舗間移動」の区別（速度・加速度センサ併用）
- → これらはすべて `.scrum/notes/radius-tradeoff.md` に記録する
