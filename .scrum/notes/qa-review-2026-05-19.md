## SwiftUI App ライフサイクルと CLLocationManager の相性（机上検証表）

### 起動経路 × 依存性生成の対応表

| 起動経路 | `App.init` | `AppDelegate.didFinish` | `WindowGroup.body` 評価 | `@State` 初期化 | dependencies 生成 | delegate 設定 |
|---|---|---|---|---|---|---|
| **アプリアイコンタップ**（通常） | ◯ | ◯（AppDelegate あれば） | ◯ | ◯ | ◯ | ◯ |
| **タスクキル → 再起動**（手動） | ◯ | ◯ | ◯ | ◯ | ◯ | ◯ |
| **SLC バックグラウンド起床** | △（実装による） | ◯（AppDelegate あれば） | **❌**（UI が描画されないため body 評価されないケースあり） | **❌** | AppDelegate 経由なら ◯ | AppDelegate 経由なら ◯ |
| **`UIBackgroundModes: location` 復帰** | △ | ◯ | **❌** | **❌** | AppDelegate 経由なら ◯ | AppDelegate 経由なら ◯ |
| **Push 通知経由起動** | ◯ | ◯ | ◯ | ◯ | ◯ | ◯ |
| **Universal Link 経由起動** | ◯ | ◯ | ◯ | ◯ | ◯ | ◯ |

### 重要ポイント

1. **SLC バックグラウンド起床 / Background mode 復帰では `WindowGroup.body` が評価されないケースがある**
   - iOS は UI を描画する必要が無いと判断すると body を呼ばない
   - `@State private var dependencies = AppDependencyContainer()` は body 評価まで初期化されないため、**そもそも `LocationService` のインスタンスが存在しない**
2. **AppDelegate 経由なら body 評価に依存せず生成可能**
   - `UIApplicationDelegateAdaptor` で AppDelegate を立てる
   - `AppDelegate.application(_:didFinishLaunchingWithOptions:)` 内で `AppDependencyContainer()` を生成
   - `launchOptions[.location] != nil` で「これは位置情報による起床」を検知できる
3. **App.init() でも保険として生成しておく**
   - SwiftUI Scene 構築順序によっては App.init が AppDelegate.didFinish より先に呼ばれるケースもある
   - 両方で生成しても問題ないよう、`AppDependencyContainer` を冪等にする（shared 経由 / 単一インスタンス保証）

### CLLocationManager 側の delegate 要件

| delegate メソッド | S6-015 以前 | S6-019 以降 |
|---|---|---|
| `locationManager(_:didUpdateLocations:)` | ◯ 実装済 | ◯ 実装済 |
| `locationManager(_:didChangeAuthorization:)` | ◯ 実装済 | ◯ 実装済 |
| `locationManager(_:didFailWithError:)` | ◯ 実装済 | ◯ 実装済 |
| `locationManagerDidPauseLocationUpdates(_:)` | **❌ 未実装** | **◯ 実装**（S6-019） |
| `locationManagerDidResumeLocationUpdates(_:)` | **❌ 未実装** | **◯ 実装**（S6-019） |
| `locationManagerDidChangeAuthorization(_:)`（iOS 14+） | ◯ 実装済 | ◯ 実装済 |

`pause/resume` の delegate が無い + `pausesLocationUpdatesAutomatically=true` の組合せは、本アプリのコア要件（「移動経路を常に記録」）と構造的に相性が悪い。S6-019 で `pause=false` に倒す + 防御的に delegate を実装する。

## 既存 256 件テストの構造的限界

### 何を検証しているか

S6-001 以降に追加した DI カバレッジテストを含め、既存 256 件は以下のスタイル:

```swift
// 既存テストの典型パターン
@MainActor
func test_someBehavior() async throws {
    let mockManager = MockCLLocationManager()
    let locationService = LocationService(
        manager: mockManager,
        appSettings: AppSettings.preview,
        tripRepository: MockTripRepository()
    )

    // mockManager.simulate(locations: ...)
    // locationService.method() の検証
}
```

→ **「LocationService の単体検証」としては高品質**。回帰検知力も十分。

### 何を検証していないか

- **`App.init` → `UIApplicationDelegateAdaptor.application(_:didFinishLaunchingWithOptions:)` → `WindowGroup.body` 評価の連鎖**
- **`@State` / `@StateObject` の初期化タイミング**
- **`launchOptions[.location]` 経由の SLC 起床経路**
- **`AppDelegate.shared` のライフサイクル**

### 結果として何が起きたか

- S6-015: ユニットテスト 4 件 pass → 実機で「タスクキル後の自宅 → 再出発」NG
- S6-016: ユニットテスト 3 件 pass → 実機で「タブ切替で記録停止」NG
- S6-017: ユニットテスト 3 件以上 pass → 実機で「自宅出発直後の記録欠落」NG
- 2026-05-19: ユニットテスト 252 件 pass → 実機で「タスクキル中は GPS が反応しない」NG

→ **「ユニットテストは pass するのに実機で機能しない」を 4 回繰り返した**。これは構造的検出漏れであり、S6-020 でライフサイクル統合テストを追加して再発防止する。

### Sprint 7 への XCUITest 整備提案

XCTest level の統合テスト（S6-020）でも、以下は検証できない:
- **真の SLC バックグラウンド起床経路**: 実機 / シミュレータで OS が SLC で起床させた状態
- **`UIBackgroundModes: location` 復帰**: バックグラウンド継続実行の挙動
- **タブ切替 / シート表示の `.onAppear` / `.onDisappear` 順序**
- **アプリのスリープ → 復帰時のスレッド状態**

→ **Sprint 7 で XCUITest セットアップ + e2e ライフサイクル系テスト 3〜5 件追加** を S7-001 候補としてチケット化する提案。
