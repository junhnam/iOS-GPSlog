# StayDetector 半径選定の経緯（radius tradeoff）

最終更新: 2026-05-09（Sprint 6 実機検証 1 回目フィードバック反映 / S6-012 起票）
背景: jun さんの実機検証で「4 店舗で各 20 分滞在 → ピン 1 件のみ」というバグを検出。半径 30m を 100m に拡大する判断を記録する。

---

## 1. 30m → 100m への変更経緯

### Sprint 2 (S2-006) 時点の選定根拠（30m）

- GPS 精度（kCLLocationAccuracyBest = 約 5〜10m）に揺らぎマージンを足した値として 30m を採用
- **想定シナリオ**: 喫茶店・小規模飲食店・自宅・職場など「単一の建物内に居続ける」ケース
- 想定外シナリオ: 大型店（モール / 家電量販店 / レストラン街）での店内回遊

### Sprint 6 実機検証 1 回目（2026-05-09 夕方）で判明した課題

- jun さんが iPhone 16 Pro で 4 店舗 × 各 20 分滞在 → ピン 1 件しか記録されなかった
- 原因: 大型店内で 30m 以上歩く → アンカー切替 → 累積時間 < `minDuration` → ピン未生成のまま新アンカーへ → 同じ動作の繰り返し
- 詳細は [`.scrum/tickets/S6-012.md`](../tickets/S6-012.md) 参照

### jun さんの判断（2026-05-09 メイン代行確認済）

| 論点 | 回答 |
|---|---|
| 半径の値 | **100m** に拡大（大型店対応優先）|
| 設定画面での可変化 | **不要**（固定値で OK）|
| 商用化時の再考 | 余地あり |

---

## 2. 100m 採用のメリット

- 大型店舗（モール / 家電量販店 / レストラン街）で店内回遊しても累積滞留時間が分断されない
- jun さんの実機シナリオ（4 店舗 20 分 → ピン 1 件）を解消できる見込み
- CLAUDE.md「お店情報を紐付ける」要件の実用性が向上（大型店こそ「どこ行ったか」を後で見たい）
- フードコート・複合商業施設での滞留検知にも有効

---

## 3. 100m 採用のデメリット / トレードオフ

### A. 隣接する別店舗を同一視するリスク

- 例: コンビニ A（100m 圏内）→ バス停（同 100m 圏内）→ 隣接する店 B → アンカーが切り替わらず 1 件のピンとしてマージされる
- 商店街・駅前繁華街など「店舗が密集している」エリアで顕著
- 個人利用としての許容判断: jun さんは「大型店優先」を選択（小規模店の取りこぼしより、大型店での 0 件検出の方が痛い）

### B. GPS 精度誤差を吸収しすぎる

- kCLLocationAccuracyBest = 約 5〜10m に対し、100m は 10〜20 倍の余裕
- 屋内 / 高層ビル谷間で精度が落ちた場合に「移動したのに同じ場所」と誤判定する可能性
- 個人利用としての許容判断: 屋内シナリオこそピン化したい本来の用途と一致するため許容

### C. MKLocalSearch / 店舗名取得の精度との不整合

- `PlaceLookupService` が拾うお店情報は座標 ±数十 m の精度に依存
- 100m 圏内に複数店舗がある繁華街では「ピンの座標」と「実際に滞留した店舗」がズレる可能性
- 個人利用としての許容判断: S6-011（ピンタップ詳細 + 外部マップ起動）で「住所 + Apple/Google Maps を開く」導線を提供しているため、ズレは事後修正可能

### D. 冪等性ガードへの波及

- `RetroactiveStayDetector.isDuplicate` も `StayDetectionConfig.radiusMeters` を共有 → 100m に追従
- 100m + 5 分（`minDuration / 2`）以内の既存ピンと「同一」とみなされる範囲が広がる
- 副作用: 同じ場所に同時刻 5 分差で 2 回滞留（来店 → 退店 → 再来店）した場合、1 件にマージされる
- 個人利用としての許容判断: 現実的にレアシナリオのため許容

## 4. なぜ「設定画面での可変化」を採用しなかったか

jun さん判断（2026-05-09）:

- 個人利用版では「固定値で動けば OK」「設定項目を増やすと UI が煩雑になる」
- 商用化時には再検討（複数ペルソナ対応の余地）
- 開発工数の圧縮: S6-012 を S サイズに収めるために設定 UI / AppSettings 拡張は省略

**Sprint 7 以降での再検討トリガー**:

- 100m でも実機検証で取りこぼしが起きる → 値の再選定 or 動的化
- jun さん以外のユーザーから「半径を変えたい」要望 → 設定 UI 化
- 商用化判断時の競合分析

## 5. 代替案（採用見送り）

### 案 1: 半径を 50m にする（折衷案）

- 採用見送り理由: jun さんの実機シナリオ（4 店舗 20 分）が 50m でも分断される可能性が残る（大型店は 100m 超えが普通）
- 折衷案は「どっちつかず」になりやすい

### 案 2: 滞留判定アルゴリズムの精緻化（密度ベース / クラスタリング）

- 採用見送り理由: Sprint 6 のスコープ外（個人利用版リリースを優先）
- Sprint 7 以降の改善候補として記録

### 案 3: 移動速度連動（速度が低い時は半径を広げる）

- 採用見送り理由: CLLocation の `speed` プロパティの精度問題 / 静止状態の判定ロジックが複雑化
- 商用化時の検討候補

### 案 4: 「店舗内回遊」と「店舗間移動」の区別（速度 + 加速度センサ併用）

- 採用見送り理由: CoreMotion 連携が必要 / 権限追加 / バッテリー懸念再燃
- 商用化版での検討候補（「歩行 / 走行 / 静止」の判定 API は存在）
